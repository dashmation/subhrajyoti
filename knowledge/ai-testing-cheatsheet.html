1. AI Testing Fundamentals

Understanding how AI testing differs from traditional software testing — non-determinism, data dependency, and emergent behavior require new testing paradigms.

Traditional vs AI Testing

AspectTraditional TestingAI/ML Testing
OutputDeterministic — same input always gives same outputNon-deterministic — outputs may vary across runs
Test OracleClear expected resultsApproximate/statistical expected results
Code vs DataBugs in code logicBugs in code, data, model, or training process
CoverageLine/branch/path coverageData coverage, feature coverage, fairness coverage
RegressionSame tests, same results expectedModel retraining may change behavior — drift detection needed
Edge CasesBoundary values, null checksAdversarial inputs, distribution shifts, hallucinations

16. Interview Q&A (50+ Questions)

Comprehensive Q&A covering AI testing concepts from basic to advanced — designed to help you crack any AI/Agentic AI testing interview.

🟢 Fundamentals (Basic)

Q1: How is AI testing different from traditional software testing?

Answer: Traditional testing has deterministic outputs (same input = same output), clear pass/fail criteria, and focuses on code logic. AI testing deals with non-deterministic outputs, statistical validation (accuracy thresholds instead of exact matches), data-dependent behavior, and emergent properties. AI testing must also handle concept drift, model degradation, and fairness across populations — concerns that don't exist in traditional testing.

Q2: What is the AI Testing Pyramid? How does it differ from the traditional test pyramid?

Answer: The AI testing pyramid extends the traditional pyramid with data-specific layers: Base: Data quality tests (schema, completeness, drift) + unit tests for transforms. Middle: Model evaluation tests (accuracy, fairness, robustness) + integration tests. Top: End-to-end behavioral tests + system tests. Above pyramid: Production monitoring (drift detection, performance tracking). The key difference is data validation runs at every level, and the "test oracle" problem means we use statistical thresholds rather than exact expected values.

Q3: What is a test oracle problem in AI testing?

Answer: The test oracle problem in AI refers to the difficulty of defining "correct" output for AI systems. Unlike traditional software where expected outputs are clear, AI outputs (especially from generative models) don't have a single correct answer. Solutions include: (1) Statistical thresholds (accuracy > 0.85), (2) Human evaluation with rubrics, (3) LLM-as-judge patterns, (4) Relative evaluation (new model vs baseline), (5) Behavioral testing with invariance/directional tests.

Q4: Explain the CheckList methodology for NLP testing.

Answer: CheckList (from Microsoft Research) provides structured behavioral testing for NLP models with three test types: MFT (Minimum Functionality Test): Simple, clear-cut test cases with known correct answers. INV (Invariance Test): Input perturbations that shouldn't change the output (e.g., synonym substitution, name changes). DIR (Directional Test): Perturbations with known directional effect (e.g., adding "but terrible" should push sentiment negative). This approach tests capabilities (vocabulary, negation, robustness) rather than just overall accuracy.

Q5: What metrics would you use to evaluate a classification model? When would you choose each?

Answer: Accuracy: When classes are balanced. Precision: When false positives are costly (spam detection — don't wrongly block legitimate email). Recall: When false negatives are dangerous (cancer detection — don't miss a diagnosis). F1 Score: When you need balance between precision and recall. AUC-ROC: When threshold-independent evaluation is needed or class imbalance exists. PR-AUC: Better than ROC for highly imbalanced datasets. Always use multiple metrics and evaluate per-class for multi-class problems.

🟡 Intermediate (ML & LLM Testing)

Q6: How do you test for data drift? What are the types of drift?

Answer: Types of drift: Data/Covariate Drift: Input feature distributions change (e.g., user demographics shift). Concept Drift: Relationship between input and output changes (e.g., "spam" definition evolves). Prediction Drift: Model output distribution changes. Label Drift: Target variable distribution changes. Detection methods: KS-test and chi-square test for statistical comparison, PSI (Population Stability Index), Evidently AI for automated reports, and monitoring feature statistics over time windows.

Q7: How do you test an LLM for hallucinations?

Answer: Hallucination testing approaches: (1) Faithfulness scoring: Compare output claims against provided context using NLI models or LLM-as-judge. (2) Factual consistency: Cross-reference with knowledge base. (3) Self-consistency: Ask same question multiple times; inconsistent answers suggest hallucination. (4) Attribution testing: Require citations, verify they exist and support claims. (5) Unknowable questions: Ask things the model shouldn't know; it should express uncertainty. Tools: DeepEval's HallucinationMetric, RAGAS faithfulness, SelfCheckGPT.

Q8: What is "LLM-as-judge" and what are its limitations?

Answer: LLM-as-judge uses a powerful LLM (e.g., GPT-4) to evaluate outputs of another model, replacing human evaluation. It can score relevance, coherence, safety, etc. Limitations: (1) Position bias — prefers first option in comparisons. (2) Self-enhancement bias — prefers outputs from same model family. (3) Verbosity bias — prefers longer answers. (4) Cost and latency of evaluation. (5) Inconsistency across runs. Mitigations: Use rubrics, randomize position, use multiple judges, calibrate against human ratings.

Q9: How would you set up A/B testing for an AI model in production?

Answer: Steps: (1) Define success metrics (conversion, satisfaction, task completion). (2) Determine sample size using power analysis. (3) Set up traffic splitting (feature flags or load balancer). (4) Run both models simultaneously on random user segments. (5) Collect metrics for statistical significance (typically 2+ weeks). (6) Use statistical tests (t-test, chi-square) to compare. (7) Account for novelty effect and learning curves. Considerations: Ensure no selection bias, handle network effects, define guardrail metrics (latency, errors) alongside primary metrics.

Q10: Explain the difference between shadow testing and canary deployment for AI models.

Answer: Shadow testing: New model runs alongside production model, receives same requests, but its responses are NOT served to users — only logged for comparison. Zero risk to users, good for validating accuracy before deployment. Canary deployment: New model serves a small percentage (e.g., 5%) of real traffic. Users see the new model's responses. Allows monitoring real-world impact but carries some risk. Use shadow first to validate quality, then canary to validate user-facing behavior before full rollout.

Q11: How do you test a RAG (Retrieval-Augmented Generation) system?

Answer: Test each component separately and together: Retriever: Precision@K, Recall@K, MRR — are relevant docs retrieved? Chunking: Semantic integrity, no mid-sentence splits. Generator: Faithfulness (grounded in context), relevance, correctness. E2E: Answer correctness against golden set. Failure modes to test: Retrieval misses, context poisoning (irrelevant docs mislead LLM), hallucination despite good context, multi-hop reasoning failures, appropriate refusal when answer isn't in knowledge base. Use RAGAS framework for automated RAG evaluation.

Q12: What is prompt injection and how do you test for it?

Answer: Prompt injection is when users manipulate input to override system instructions or extract sensitive information. Types: Direct (user input attempts override), Indirect (malicious content in retrieved documents/tool outputs). Testing: (1) Attempt system prompt extraction. (2) Try role-play/DAN attacks. (3) Use encoding tricks (base64, ROT13). (4) Test multi-turn escalation. (5) Inject instructions in tool outputs. (6) Try context overflow attacks. Defenses to verify: Input sanitization, output filtering, system prompt hardening, separate data and instruction channels.

🔴 Advanced (Agentic AI Testing)

Q13: What makes testing agentic AI systems fundamentally harder than testing traditional AI?

Answer: Agentic AI introduces: (1) Non-deterministic execution paths — same task may be solved differently each run. (2) Emergent behavior — actions produce unexpected consequences. (3) Compounding errors — one bad decision cascades through multi-step execution. (4) State management — agents maintain memory/context that affects future decisions. (5) External world interaction — tool calls have real side effects (sending emails, writing files). (6) Evaluation complexity — many valid paths to a correct answer. (7) Safety boundaries — must never exceed permissions regardless of reasoning.

Q14: How would you test a multi-agent system where agents collaborate?

Answer: Multi-agent testing layers: (1) Individual agent: Test each agent's core capability in isolation. (2) Communication: Verify message format, completeness, and interpretation between agents. (3) Coordination: Test task delegation, dependency ordering, parallel execution. (4) Conflict resolution: What happens when agents disagree or compete for resources? (5) Emergent behavior: Chaos testing — inject failures, delays, corrupted messages. (6) Consensus: Test voting/agreement mechanisms. (7) End-to-end: Full system produces correct final output. Key metrics: task success rate, coordination overhead, degradation under failures.

Q15: Describe your approach to testing an AI agent's tool-use capabilities.

Answer: Layered testing approach: Level 1 - Tool Unit Tests: Each tool works correctly with valid inputs, handles errors gracefully, validates schemas. Level 2 - Tool Selection: Agent picks the right tool for a given task (use labeled dataset of queries→expected tools). Level 3 - Parameter Extraction: Agent correctly extracts parameters from natural language (date formats, entity names). Level 4 - Error Recovery: Agent handles tool timeouts, rate limits, invalid responses. Level 5 - Security: Agent doesn't follow malicious instructions in tool outputs (indirect injection). Level 6 - Efficiency: Agent uses minimum necessary tool calls, parallelizes when possible.

Q16: How do you test for infinite loops and runaway costs in agentic systems?

Answer: Safeguards to test: (1) Max step limits: Verify agent stops after N steps. (2) Token budgets: Test that cost guardrails trigger correctly. (3) Loop detection: Monitor for repeated identical actions/states. (4) Timeout enforcement: Verify hard time limits. (5) Cost tracking: Real-time token counting with abort thresholds. Testing approach: Create scenarios that naturally induce loops (circular dependencies, impossible tasks, conflicting instructions) and verify the agent gracefully terminates with an explanation rather than running indefinitely.

Q17: What is the ReAct pattern and how do you test it?

Answer: ReAct (Reasoning + Acting) interleaves thought, action, and observation: Think → Act → Observe → Think → Act → ... Testing: (1) Thought quality: Reasoning is logical and relevant to the task. (2) Action alignment: Actions follow from reasoning (not random). (3) Observation usage: Agent incorporates observation results into next thought. (4) Convergence: Loop converges toward task completion. (5) Error handling: When observation shows failure, agent adjusts plan. Validate by capturing full traces and evaluating each step's coherence with the overall goal.

Q18: How do you handle non-determinism in AI testing? How do you make tests reliable?

Answer: Strategies: (1) Statistical testing: Run tests N times, pass if success rate > threshold (e.g., 90% over 10 runs). (2) Temperature=0: Reduce randomness for deterministic-ish outputs (still not guaranteed). (3) Semantic assertions: Check meaning rather than exact text (LLM-as-judge, embedding similarity). (4) Property-based testing: Verify properties that must always hold (response length < 500, contains no PII, is valid JSON). (5) Fuzzy matching: Use cosine similarity > 0.85 instead of exact match. (6) Behavioral contracts: Define invariants that must hold regardless of specific output.

Q19: How would you design a test suite for an AI coding assistant (like GitHub Copilot)?

Answer: Test dimensions: (1) Code correctness: Generated code passes unit tests (HumanEval, MBPP benchmarks). (2) Code quality: Passes linters, follows style guides, no security vulnerabilities. (3) Context understanding: Uses existing code patterns, imports correct libraries. (4) Instruction following: Respects language choice, framework preferences. (5) Safety: Doesn't generate malicious code, SQL injection, hardcoded secrets. (6) Regression: Golden set of prompt→code pairs. (7) Performance: Latency acceptable for interactive use. (8) Multi-turn: Maintains context across conversation turns. Use pass@k metric (probability of at least one correct solution in k attempts).

Q20: What is the difference between evaluation and testing for LLMs?

Answer: Evaluation: Measuring model capabilities using benchmarks and metrics (accuracy, BLEU, human preference). Answers "how good is this model?" Used during development to compare models/prompts. Testing: Verifying specific behaviors and requirements are met. Answers "does this meet our requirements?" Used in CI/CD with pass/fail gates. Key difference: Evaluation informs decisions (which model to use), testing enforces standards (this PR cannot merge if hallucination rate > 10%). Both are needed — evaluation for development, testing for deployment.

Q21: How do you test memory and context management in a conversational AI agent?

Answer: Test areas: (1) Short-term memory: Agent remembers info from earlier in conversation. (2) Long-term memory: Agent recalls user preferences across sessions. (3) Memory accuracy: Stored facts are correct (no memory corruption). (4) Memory relevance: Agent retrieves relevant memories for current context. (5) Memory bounds: System handles context window limits gracefully. (6) Forgetting: Sensitive information is appropriately forgotten. Test with multi-turn conversations that reference earlier information, contradictory updates (does agent use latest info?), and memory-heavy scenarios near token limits.

Q22: How would you implement continuous evaluation for an LLM application in production?

Answer: Architecture: (1) Log all interactions: Input, output, context, metadata, latency. (2) Async evaluation: Run quality metrics on sampled outputs (don't block serving). (3) Human feedback loop: Thumbs up/down, escalation tracking. (4) Automated alerts: Hallucination rate spike, latency degradation, cost anomaly. (5) Drift detection: Compare input distributions weekly against training data. (6) Regression dashboards: Track key metrics over time. (7) A/B analysis: Continuous comparison when rolling out changes. Tools: LangSmith for tracing, Evidently for drift, custom dashboards in Grafana.

Q23: What are guardrails in AI systems and how do you test them?

Answer: Guardrails are safety mechanisms that constrain AI behavior: Input guardrails: Filter/block malicious inputs (prompt injection, toxic content). Output guardrails: Scan outputs for PII, toxicity, hallucinations before serving. Behavioral guardrails: Prevent agent from performing dangerous actions. Testing: (1) Red-team with adversarial inputs that should be blocked. (2) Verify legitimate inputs are NOT blocked (false positive rate). (3) Test bypass attempts (encoding, multi-turn, role-play). (4) Measure latency overhead of guardrails. (5) Test graceful fallback when guardrails trigger. Tools: Guardrails AI, NeMo Guardrails, custom validators.

Q24: Explain how you would test an AI agent that can browse the web, write files, and execute code.

Answer: This high-risk agent needs defense-in-depth testing: Sandboxing: Verify agent runs in isolated environment (container, VM). Permission boundaries: Test that agent cannot access restricted paths, networks, or APIs. Action confirmation: Verify destructive actions require approval. Output sanitization: Generated code is scanned for malware patterns. Resource limits: CPU, memory, disk, and network quotas are enforced. Audit logging: Every action is logged with full trace. Rollback testing: Verify file changes can be reverted. Injection resistance: Web pages with malicious content don't compromise the agent. Use scenario-based testing with both benign tasks and adversarial scenarios.

Q25: How do you measure and improve the "reasoning quality" of an AI agent?

Answer: Reasoning quality metrics: (1) Logical consistency: Conclusions follow from premises (check with NLI models). (2) Plan completeness: All necessary steps identified. (3) Step efficiency: No redundant reasoning steps. (4) Self-correction: Agent identifies and fixes its own errors. (5) Uncertainty calibration: Agent's confidence matches actual accuracy. Improvement methods: Chain-of-thought prompting, reflection/critique loops, constitutional AI training, process reward models (reward each step, not just final answer). Test using annotated reasoning traces with human-evaluated quality scores.

🎯 Scenario-Based & Expert Questions

Q26: Your LLM chatbot's user satisfaction score dropped 15% after a model update. How do you investigate?

Answer: Investigation plan: (1) Compare metrics: Look at hallucination rate, refusal rate, latency, response length before/after. (2) Slice analysis: Which user segments, query types, or topics are affected? (3) Sample review: Manually review 50+ conversations showing low scores. (4) Regression test: Run golden set against old and new model, compare. (5) A/B analysis: If still in canary, compare canary vs baseline cohorts. (6) Root cause: Check if prompt template changed, context window differs, temperature settings, or knowledge cutoff date. (7) Quick fix: Rollback if critical, then address root cause before redeploying.

Q27: Design a test strategy for a customer support AI agent that can access order history, issue refunds, and escalate to humans.

Answer: Test strategy layers: Happy paths: Correctly looks up order, processes refund within policy, updates customer. Edge cases: Expired refund window, partial refunds, multiple items, cancelled orders. Authorization: Agent can only refund within limits (e.g., < $500), escalates higher amounts. Safety: Cannot refund to different accounts, reveals only customer's own data. Escalation: Correctly identifies when to hand off (complex issues, angry customers, legal questions). Context: Handles multi-turn conversations, remembers order details discussed earlier. Load: 100 concurrent conversations without degradation. Monitoring: Track refund accuracy, false escalation rate, customer satisfaction.

Q28: How do you test for bias in a hiring AI system?

Answer: Comprehensive bias testing: (1) Demographic parity: Selection rates should be similar across groups. (2) Counterfactual testing: Change only protected attributes (name, gender, age) and verify scores don't change. (3) Disparate impact: Check if selection rate for any group < 80% of highest group (4/5ths rule). (4) Proxy detection: Identify features that correlate with protected attributes (zip code → race). (5) Historical bias: Training data may embed past discrimination. (6) Intersectional: Test combinations (e.g., Black women, older disabled). Tools: AIF360, Fairlearn, custom counterfactual test suites. Legal compliance: EEOC guidelines, local AI regulations (EU AI Act).

Q29: What is "evaluation-driven development" for AI applications?

Answer: Evaluation-driven development (EDD) applies TDD principles to AI: (1) Write evals first: Before changing prompts/models, define what "good" looks like with test cases. (2) Baseline measurement: Run evals on current system to establish baseline. (3) Iterate: Make changes, run evals, compare to baseline. (4) Gate deployments: Changes only deploy if evals pass thresholds. Benefits: Prevents prompt engineering guesswork, provides objective progress measurement, enables team collaboration (shared eval criteria). Implementation: Use promptfoo or DeepEval in CI/CD, maintain growing eval datasets, track metrics over time.

Q30: How do you test an AI system for regulatory compliance (GDPR, EU AI Act)?

Answer: Compliance testing areas: GDPR: (1) Right to erasure — verify training data can be removed. (2) Data minimization — only necessary data collected. (3) No PII in outputs. (4) User consent before data processing. EU AI Act: (1) Risk classification — is system high-risk? (2) Transparency — users know they're interacting with AI. (3) Human oversight — escalation mechanisms work. (4) Documentation — technical documentation complete. (5) Bias testing — fairness across protected characteristics. Testing: Automated PII scanning, audit trail verification, consent flow testing, documentation completeness checks, third-party audits.

Q31: Explain how you would implement and test a "human-in-the-loop" pattern for an AI agent.

Testing: (1) Trigger accuracy: Agent correctly identifies actions requiring approval (destructive, high-cost, irreversible). Q32: What is "Constitutional AI" testing?

Answer: Constitutional AI (from Anthropic) trains models to follow a set of principles ("constitution") through self-critique. Testing constitutional behavior: (1) Principle adherence: Model outputs align with stated principles (helpful, harmless, honest). (2) Self-critique quality: Model identifies its own violations correctly. (3) Revision quality: Self-corrections actually improve the output. (4) Robustness: Constitution holds under adversarial pressure. (5) Completeness: Constitution covers all necessary safety areas. Test approach: Create scenarios that test each constitutional principle, verify model's self-assessment matches human assessment.

Q33: How do you test the "memory" of a long-running AI agent across multiple sessions?

Answer: Memory testing dimensions: (1) Storage: Information is correctly persisted between sessions. (2) Retrieval: Relevant memories surface when needed (semantic search quality). (3) Accuracy: Retrieved memories are faithful to originals (no corruption). (4) Recency: Recent information takes priority over outdated info. Q35: What is "model drift" and how do you set up automated detection?

Answer: Model drift occurs when model performance degrades over time due to changing data patterns. Types: Training-serving skew, concept drift, data drift. Automated detection setup: (1) Establish baseline metrics during deployment. (2) Continuously compute metrics on production predictions. (3) Statistical tests (KS-test, PSI) on sliding windows. (4) Set alert thresholds (e.g., accuracy drop > 3%). (5) Automated retraining triggers when drift exceeds threshold. (6) Dashboards showing metric trends. Tools: Evidently AI, NannyML, WhyLabs, custom Prometheus metrics. Key: Need delayed ground truth to measure actual drift vs. just input distribution changes.

Q36: How do you test function/tool calling in production LLMs (OpenAI, Claude)?

Answer: Test layers: (1) Schema compliance: Generated JSON matches tool's JSON Schema. (2) Tool selection accuracy: Right tool chosen from available set. (3) Parameter correctness: Values extracted correctly from user input. (4) Required vs optional: Required params always provided, optional only when relevant. Q37: Describe the testing strategy for deploying an AI agent in a regulated industry (healthcare, finance).

Answer: Regulated AI testing adds layers: (1) Accuracy requirements: Higher thresholds (99%+ for medical diagnosis assistance). (2) Explainability: Model decisions must be interpretable (SHAP, LIME). (3) Audit trails: Every decision logged with reasoning. (4) Human oversight: Critical decisions require human confirmation. (5) Bias testing: Certified fairness across protected groups (adverse impact analysis). (6) Robustness: Adversarial testing for worst-case scenarios. (7) Versioning: Complete lineage (data version → model version → decision). (8) Validation studies: Clinical trials (healthcare) or backtesting (finance). Q38: What is "process reward modeling" and how does it apply to testing agent reasoning?

Answer: Process Reward Models (PRMs) evaluate each reasoning step individually, not just the final answer. Unlike Outcome Reward Models (ORMs) that only judge the end result. Application to testing: (1) Each step in agent's reasoning chain gets a quality score. (2) Can identify exactly where reasoning goes wrong (step 3 was invalid). (3) Enables granular feedback for improvement. (4) Better for complex multi-step tasks where correct process matters. Testing implementation: Annotate reasoning traces step-by-step, train a PRM, use it to automatically score agent reasoning quality in evaluation pipelines. This catches agents that get right answers through wrong reasoning (lucky guesses).

Q39: How do you test an AI system's ability to "know what it doesn't know" (calibration)?

Answer: Calibration testing verifies that confidence levels match actual accuracy: (1) Expected Calibration Error (ECE): Group predictions by confidence, compare confidence to accuracy per bin. (2) Selective prediction: Does model abstain/say "I don't know" on questions outside its knowledge? (3) Verbalized uncertainty: Does language like "I'm not sure" correlate with actual error likelihood? (4) Out-of-distribution detection: Model flags inputs that differ from training distribution. Tests: Mix known questions with unknowable ones, verify model's confidence is lower on harder/unknowable questions. A well-calibrated model with 80% confidence should be correct ~80% of the time.

Q40: How do you test AI agents in an environment where actions have real-world consequences?

Answer: Progressive testing strategy: (1) Simulation: Fully mocked environment — test all logic without real effects. (2) Sandbox: Real systems but isolated (test database, staging APIs). (3) Dry-run mode: Agent plans actions but doesn't execute — human reviews plan. (4) Limited scope: Real execution but with tight constraints (small amounts, read-only first). (5) Canary: Small % of real traffic with monitoring. (6) Full production: With guardrails, monitoring, and kill switch. Each stage should pass before advancing. Always maintain ability to undo actions (compensating transactions, rollback mechanisms).

Q45: What is "metamorphic testing" and how does it apply to AI?

Answer: Metamorphic testing defines relationships between inputs/outputs rather than exact expected values — perfect for AI where exact outputs are unknown. Metamorphic relations for AI: (1) Permutation: Reordering input list shouldn't change classification. (2) Scaling: Doubling all features shouldn't change relative ranking. (3) Negation: Adding "not" should flip sentiment. (4) Addition: Adding irrelevant info shouldn't change answer. (5) Consistency: "A is better than B" and "B is better than A" shouldn't both pass. This solves the test oracle problem by testing relationships rather than absolute correctness.

Q48: What are "evals" in the LLM context and how do you build a good eval suite?

Q52: What is the difference between "online" and "offline" evaluation for AI systems?

Answer: Offline evaluation: Run before deployment on static datasets. Includes: benchmark testing, regression suites, golden set evaluation. Advantages: Controlled, repeatable, cheap. Limitations: May not reflect real user behavior. Online evaluation: Run on live traffic in production. Includes: A/B tests, canary metrics, user feedback, production monitoring. Advantages: Reflects real-world performance. Limitations: Slower feedback loop, risk to users. Best practice: Gate with offline evals (fast, cheap, catches regressions), then validate with online evals (real-world confirmation). Neither alone is sufficient.

Q53: How do you ensure reproducibility in AI testing?

Answer: Reproducibility challenges in AI: Non-deterministic outputs, changing APIs, data drift. Solutions: (1) Seed control: Fix random seeds where possible (temperature=0). (2) Version pinning: Pin model version, API version, library versions. (3) Data snapshots: Version control test data (DVC). (4) Environment capture: Docker containers for consistent environments. (5) Deterministic ordering: Fixed test case order. (6) Statistical tests: When exact reproducibility impossible, use confidence intervals (pass if 9/10 runs succeed). (7) Trace logging: Save full model inputs/outputs for debugging. Accept that some non-determinism is inherent — design tests to be robust to it.
