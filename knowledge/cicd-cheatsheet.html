1. Jenkins Basics

Jenkins is the most widely-used CI/CD server — understanding its job types and UI is the starting point.

ConceptDescriptionExample
Installation (Docker) Run Jenkins in a Docker container with persistent volume
▶ Show
docker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts-jdk17

# Get initial admin password
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
Installation (Linux) Install Jenkins on Ubuntu/Debian via apt
▶ Show
# Add Jenkins repo key and source
curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key | sudo tee \
  /usr/share/keyrings/jenkins-keyring.asc > /dev/null
echo deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null

sudo apt update && sudo apt install jenkins -y
sudo systemctl enable --now jenkins
# Access at http://localhost:8080

2. Jenkins Pipeline (Declarative Syntax)

Pipeline-as-code (Jenkinsfile) makes CI/CD reproducible, versioned, and reviewable like application code.

ConceptDescriptionExample
Basic Structure pipeline → agent → stages → stage → steps. The minimal skeleton.
▶ Show
pipeline {
    agent any
    // Use any available executor

    stages {
        stage('Build') {
            steps {
                sh 'mvn clean compile'
            }
        }
        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }
        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
Agent Types Where the pipeline runs: any, none, label, docker, kubernetes
▶ Show
agent any                    // Any available agent
agent none                   // No global agent (set per stage)
agent { label 'linux' }      // Agent with label
agent {
    docker {
        image 'maven:3.9-eclipse-temurin-17'
        args '-v /root/.m2:/root/.m2'
    }
}
agent {
    kubernetes {
        yaml '''
        apiVersion: v1
        kind: Pod
        spec:
          containers:
          - name: maven
            image: maven:3.9-jdk-17
            command: ['sleep', '99d']
        '''
    }
}
Environment Set env vars for entire pipeline or specific stages
▶ Show
pipeline {
    agent any
    environment {
        APP_NAME = 'my-app'
        VERSION  = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
        CREDS    = credentials('my-secret-id') // Injects USERNAME and PASSWORD
    }
    stages {
        stage('Print') {
            environment {
                STAGE_VAR = 'only-here'
            }
            steps {
                sh 'echo $APP_NAME $VERSION $STAGE_VAR'
            }
        }
    }
}
Tools Auto-install and add to PATH: maven, jdk, gradle, nodejs
▶ Show
pipeline {
    agent any
    tools {
        maven 'Maven-3.9'    // Name from Global Tool Config
        jdk 'JDK-17'         // Name from Global Tool Config
    }
    stages {
        stage('Build') {
            steps {
                sh 'mvn --version'
                sh 'java --version'
            }
        }
    }
}
Post Actions Run after stages: always, success, failure, unstable, changed, cleanup
▶ Show
pipeline {
    agent any
    stages {
        stage('Test') {
            steps { sh 'mvn test' }
        }
    }
    post {
        always {
            junit 'target/surefire-reports/*.xml'
            archiveArtifacts artifacts: 'target/*.jar'
        }
        success {
            echo 'Build succeeded!'
        }
        failure {
            mail to: 'team@example.com',
                 subject: "FAILED: ${env.JOB_NAME}",
                 body: "Check ${env.BUILD_URL}"
        }
        cleanup {
            cleanWs() // Clean workspace
        }
    }
}
Options Pipeline-wide settings: timeout, retry, timestamps, disableConcurrentBuilds
▶ Show
pipeline {
    agent any
    options {
        timeout(time: 30, unit: 'MINUTES')
        retry(2)
        timestamps()
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '10'))
        skipDefaultCheckout()
    }
    stages { ... }
}

3. Jenkins Pipeline Advanced

Advanced pipeline features handle complex workflows — conditional execution, approvals, and matrix builds.

ConceptDescriptionExample
Parallel Stages Run multiple stages concurrently to speed up pipelines
▶ Show
stage('Tests') {
    parallel {
        stage('Unit Tests') {
            agent { label 'linux' }
            steps { sh 'mvn test -Punit' }
        }
        stage('Integration Tests') {
            agent { label 'linux' }
            steps { sh 'mvn test -Pintegration' }
        }
        stage('Lint') {
            agent { label 'linux' }
            steps { sh 'mvn checkstyle:check' }
        }
    }
}
Matrix Run stages across multiple combinations (like GitHub Actions matrix)
▶ Show
stage('Build Matrix') {
    matrix {
        axes {
            axis {
                name 'PLATFORM'
                values 'linux', 'windows', 'mac'
            }
            axis {
                name 'JDK'
                values '17', '21'
            }
        }
        excludes {
            exclude {
                axis { name 'PLATFORM'; values 'mac' }
                axis { name 'JDK'; values '17' }
            }
        }
        stages {
            stage('Build') {
                steps {
                    echo "Building on ${PLATFORM} with JDK ${JDK}"
                    sh './build.sh'
                }
            }
        }
    }
}
When (Conditionals) Execute stage only if condition matches: branch, env, expression, tag
▶ Show
stage('Deploy to Prod') {
    when {
        branch 'main'               // Only on main
    }
    steps { sh './deploy-prod.sh' }
}

stage('Deploy Staging') {
    when {
        anyOf {
            branch 'develop'
            branch 'release/*'
        }
    }
    steps { sh './deploy-staging.sh' }
}

stage('Tagged Release') {
    when {
        tag pattern: "v\\d+\\.\\d+\\.\\d+", comparator: "REGEXP"
    }
    steps { sh './release.sh' }
}

stage('Skip if no changes') {
    when {
        changeset '**/*.java'       // Only if .java files changed
    }
    steps { sh 'mvn compile' }
}
Input (Manual Approval) Pause pipeline and wait for human approval before proceeding
▶ Show
stage('Approve Deploy') {
    input {
        message 'Deploy to production?'
        ok 'Yes, deploy!'
        submitter 'admin,deploy-team'
        parameters {
            choice(name: 'ENVIRONMENT',
                   choices: ['staging', 'production'],
                   description: 'Target env')
        }
    }
    steps {
        echo "Deploying to ${ENVIRONMENT}"
        sh './deploy.sh ${ENVIRONMENT}'
    }
}
Parameters User-configurable inputs when triggering builds
▶ Show
pipeline {
    agent any
    parameters {
        string(name: 'BRANCH', defaultValue: 'main', description: 'Branch to build')
        choice(name: 'ENV', choices: ['dev','staging','prod'], description: 'Deploy target')
        booleanParam(name: 'SKIP_TESTS', defaultValue: false, description: 'Skip tests?')
        password(name: 'API_KEY', description: 'API key for deployment')
    }
    stages {
        stage('Build') {
            steps {
                echo "Building ${params.BRANCH} for ${params.ENV}"
                sh "mvn clean package ${params.SKIP_TESTS ? '-DskipTests' : ''}"
            }
        }
    }
}
Scripted Blocks Use script {} blocks inside declarative for complex Groovy logic
▶ Show
stage('Dynamic Steps') {
    steps {
        script {
            def services = ['api', 'web', 'worker']
            for (svc in services) {
                sh "docker build -t myrepo/${svc}:${env.BUILD_NUMBER} ./${svc}"
            }
            if (env.BRANCH_NAME == 'main') {
                currentBuild.description = 'Production build'
            }
        }
    }
}

4. Jenkins Shared Libraries & Plugins

Shared libraries avoid duplicating pipeline code across projects — write once, use everywhere.

ConceptDescriptionExample
Shared Library Structure Reusable code in a Git repo: vars/, src/, resources/ directories
▶ Show
# Shared library repo structure:
my-shared-library/
├── vars/
│   ├── buildJava.groovy        # Global var (callable as buildJava())
│   ├── deployToK8s.groovy
│   └── notifySlack.groovy
├── src/
│   └── com/myorg/
│       └── Utils.groovy        # Class-based utilities
├── resources/
│   └── templates/
│       └── deployment.yaml     # Resource files (libraryResource)
└── README.md
Writing a Shared Step vars/buildJava.groovy defines a call() method usable as a pipeline step
▶ Show
// vars/buildJava.groovy
def call(Map config = [:]) {
    def jdkVersion = config.jdk ?: '17'
    def goals = config.goals ?: 'clean package'

    pipeline {
        agent {
            docker { image "maven:3.9-eclipse-temurin-${jdkVersion}" }
        }
        stages {
            stage('Build') {
                steps {
                    sh "mvn ${goals} -B"
                }
            }
            stage('Archive') {
                steps {
                    archiveArtifacts artifacts: 'target/*.jar'
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }
    }
}

// Usage in Jenkinsfile:
@Library('my-shared-library') _
buildJava(jdk: '21', goals: 'clean verify')
Loading Libraries @Library annotation or library() step; configure in Manage Jenkins → System
▶ Show
// Implicit load (configured globally):
@Library('my-shared-library') _

// Specific version/branch:
@Library('my-shared-library@v2.1.0') _

// Dynamic load in pipeline:
library identifier: 'my-shared-library@main',
        retriever: modernSCM([
            $class: 'GitSCMSource',
            remote: 'https://github.com/org/jenkins-shared-lib.git',
            credentialsId: 'github-token'
        ])

5. GitLab CI Basics

GitLab CI is tightly integrated with GitLab repos — one YAML file defines your entire pipeline.

ConceptDescriptionExample
.gitlab-ci.yml Structure Root config file: define stages, then jobs that belong to stages
▶ Show
# .gitlab-ci.yml - minimal example
stages:
  - build
  - test
  - deploy

build-job:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn clean compile

test-job:
  stage: test
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn test

deploy-job:
  stage: deploy
  script:
    - ./deploy.sh
  only:
    - main
Jobs & Scripts Each job has: image, stage, script (required), before_script, after_script
▶ Show
my-job:
  image: node:20-alpine
  stage: test
  before_script:             # Runs before main script
    - npm ci
  script:                     # Main commands (required)
    - npm run lint
    - npm run test
  after_script:              # Always runs (even on failure)
    - echo "Cleanup done"
  allow_failure: false       # Fail pipeline if job fails
Stages Order Jobs in same stage run in parallel; stages run sequentially
▶ Show
stages:
  - build
  - test        # All test jobs run in parallel
  - deploy

unit-test:
  stage: test
  script: npm run test:unit

integration-test:
  stage: test
  script: npm run test:integration

lint:
  stage: test
  script: npm run lint

# ↑ All three run simultaneously in "test" stage
Image & Tags Docker image for the job; tags select specific runners
▶ Show
default:
  image: ubuntu:22.04        # Default for all jobs
  tags:
    - docker
    - linux

build-java:
  image: maven:3.9-eclipse-temurin-17  # Override per job
  tags:
    - large-runner           # Use runner with this tag
  script:
    - mvn package
Predefined Variables Auto-set variables: CI_COMMIT_SHA, CI_PIPELINE_ID, CI_JOB_NAME, etc.
▶ Show
CI_COMMIT_SHA          # Full commit hash
CI_COMMIT_SHORT_SHA    # First 8 chars
CI_COMMIT_BRANCH       # Branch name
CI_COMMIT_TAG          # Tag name (if tagged)
CI_PIPELINE_ID         # Pipeline number
CI_PROJECT_NAME        # Project name
CI_PROJECT_NAMESPACE   # Group/user namespace
CI_REGISTRY_IMAGE      # registry.gitlab.com/group/project
CI_JOB_TOKEN           # Auto token for registry/API
CI_ENVIRONMENT_NAME    # Environment name
GITLAB_USER_LOGIN      # Who triggered

6. GitLab CI Variables & Artifacts

Variables externalize secrets/config. Artifacts pass build outputs between stages.

ConceptDescriptionExample
Variables (inline) Define variables at global or job level in .gitlab-ci.yml
▶ Show
variables:                      # Global variables
  APP_NAME: "my-service"
  MAVEN_OPTS: "-Xmx512m"
  GIT_DEPTH: "5"              # Shallow clone

build-job:
  variables:                  # Job-level override
    MAVEN_OPTS: "-Xmx1g"
    BUILD_ENV: "ci"
  script:
    - echo $APP_NAME
    - mvn package $MAVEN_OPTS
Variables (CI/CD Settings) Set in GitLab UI: Settings → CI/CD → Variables. Can be masked/protected.
▶ Show
# In GitLab UI (Settings → CI/CD → Variables):
Key:       DOCKER_PASSWORD
Value:     ********
Type:      Variable
Protected: ✓   # Only on protected branches
Masked:    ✓   # Hidden in job logs
Expanded:  ✓   # Allow $VAR references in value

# File-type variable (creates a file with the content):
Key:       KUBECONFIG
Value:     (paste kubeconfig content)
Type:      File  # $KUBECONFIG becomes a file path
Artifacts Pass files between jobs; stored and downloadable from UI
▶ Show
build-job:
  stage: build
  script:
    - mvn package -DskipTests
  artifacts:
    paths:
      - target/*.jar
      - target/classes/
    exclude:
      - target/test-classes/
    expire_in: 1 week        # Auto-delete after 1 week
    when: on_success          # or always, on_failure

test-job:
  stage: test
  dependencies:
    - build-job              # Download artifacts from build-job
  script:
    - java -jar target/app.jar --test
Reports (JUnit, Coverage) Special artifact reports shown in MR UI: junit, coverage, sast, etc.
▶ Show
test-job:
  stage: test
  script:
    - mvn test
  artifacts:
    reports:
      junit: target/surefire-reports/TEST-*.xml  # MR test summary
      coverage_report:
        coverage_format: cobertura
        path: target/site/cobertura/coverage.xml
  coverage: '/Total.*?(\d+\.\d+)%/'  # Regex for badge
Cache Speed up pipelines by caching dependencies between runs
▶ Show
build-job:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  cache:
    key:
      files:
        - pom.xml            # Cache key from file hash
    paths:
      - .m2/repository
    policy: pull-push        # pull, push, or pull-push
  variables:
    MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"
  script:
    - mvn package

# Node.js example:
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - node_modules/

7. GitLab CI Advanced

Advanced features enable DAG pipelines, dynamic matrices, and environment-specific deployments.

ConceptDescriptionExample
Rules (replacing only/except) Fine-grained control: if, changes, exists with when/allow_failure
▶ Show
deploy-prod:
  stage: deploy
  script: ./deploy.sh production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual                   # Manual trigger on main
      allow_failure: false
    - if: $CI_COMMIT_TAG =~ /^v\d+/
      when: on_success              # Auto on version tags
    - when: never                     # Skip otherwise

lint:
  stage: test
  script: npm run lint
  rules:
    - changes:                      # Only if JS files changed
        - "src/**/*.{js,ts}"
        - "package.json"
    - exists:                       # Only if eslint config exists
        - .eslintrc*
Needs (DAG) Skip stage ordering; job starts as soon as needed jobs finish
▶ Show
stages:
  - build
  - test
  - deploy

build-app:
  stage: build
  script: mvn package

build-docs:
  stage: build
  script: mkdocs build

test-app:
  stage: test
  needs: [build-app]         # Starts when build-app done (not build-docs)
  script: mvn test

deploy-docs:
  stage: deploy
  needs: [build-docs]        # Doesn't wait for test-app!
  script: ./deploy-docs.sh

deploy-app:
  stage: deploy
  needs: [test-app]
  script: ./deploy-app.sh
Parallel & Matrix Split job into parallel instances with variable combinations
▶ Show
# Simple parallel (split tests):
test:
  stage: test
  parallel: 4                # Creates test 1/4, test 2/4, etc.
  script:
    - ./split-tests.sh $CI_NODE_INDEX $CI_NODE_TOTAL | xargs mvn test

# Matrix (cross-product):
test:
  stage: test
  parallel:
    matrix:
      - PLATFORM: [linux, macos]
        JDK: ['17', '21']
      - PLATFORM: [windows]
        JDK: ['21']           # 2×2 + 1×1 = 5 jobs
  image: $PLATFORM-runner:latest
  script:
    - echo "Testing on $PLATFORM with JDK $JDK"
Environments Track deployments, enable review apps, and rollback
▶ Show
deploy-staging:
  stage: deploy
  script: ./deploy.sh staging
  environment:
    name: staging
    url: https://staging.example.com
    on_stop: stop-staging    # Linked stop job

stop-staging:
  stage: deploy
  script: ./teardown.sh staging
  environment:
    name: staging
    action: stop
  rules:
    - if: $CI_COMMIT_BRANCH
      when: manual

# Review apps (dynamic environments):
review:
  stage: deploy
  script: ./deploy-review.sh
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    auto_stop_in: 1 week
  rules:
    - if: $CI_MERGE_REQUEST_IID
extends & includes Reuse config: extends for inheritance, include for multi-file
▶ Show
# Template job (starts with dot = hidden):
.java-base:
  image: maven:3.9-eclipse-temurin-17
  cache:
    paths: [.m2/repository]
  variables:
    MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"

build:
  extends: .java-base        # Inherits image, cache, variables
  stage: build
  script: mvn compile

# Include from other files/repos:
include:
  - local: ci/build.yml      # Same repo
  - project: 'group/shared-ci'
    ref: main
    file: '/templates/java.yml' # Other repo
  - remote: 'https://example.com/ci-template.yml'
  - template: Auto-DevOps.gitlab-ci.yml

8. GitLab CI Services & Docker-in-Docker

Services spin up dependencies (databases, caches) alongside your tests. DinD enables building Docker images.

ConceptDescriptionExample
Services Sidecar containers linked to job (databases, redis, etc.)
▶ Show
integration-test:
  stage: test
  image: maven:3.9-eclipse-temurin-17
  services:
    - name: postgres:15
      alias: db              # Accessible as "db" hostname
      variables:
        POSTGRES_DB: testdb
        POSTGRES_USER: test
        POSTGRES_PASSWORD: test123
    - name: redis:7-alpine
      alias: cache
  variables:
    SPRING_DATASOURCE_URL: "jdbc:postgresql://db:5432/testdb"
    SPRING_REDIS_HOST: "cache"
  script:
    - mvn test -Pintegration
Docker-in-Docker (DinD) Build Docker images inside GitLab CI using docker:dind service
▶ Show
build-image:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    DOCKER_HOST: "tcp://docker:2376"
    DOCKER_TLS_VERIFY: "1"
    DOCKER_CERT_PATH: "/certs/client"
  before_script:
    - docker info
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
Kaniko (No Docker daemon) Build images without privileged mode using Kaniko
▶ Show
build-image-kaniko:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.21.0-debug
    entrypoint: [""]
  script:
    - |
      /kaniko/executor
        --context "${CI_PROJECT_DIR}"
        --dockerfile "${CI_PROJECT_DIR}/Dockerfile"
        --destination "${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHA}"
        --destination "${CI_REGISTRY_IMAGE}:latest"
        --cache=true
        --cache-repo="${CI_REGISTRY_IMAGE}/cache"
  rules:
    - changes:
        - Dockerfile
        - src/**/*
GitLab Container Registry Built-in registry at registry.gitlab.com; auth via CI_JOB_TOKEN
▶ Show
build-and-push:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  before_script:
    - echo $CI_JOB_TOKEN | docker login -u $CI_REGISTRY_USER
        --password-stdin $CI_REGISTRY
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker build -t $CI_REGISTRY_IMAGE:latest .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - docker push $CI_REGISTRY_IMAGE:latest
  after_script:
    - docker logout $CI_REGISTRY
Docker Compose in CI Run multi-container test environments with compose

10. Docker in CI/CD

Building and pushing Docker images in CI ensures consistent, tested artifacts reach production.

ConceptDescriptionExample
Build & Push Image Build Docker image, tag with commit SHA + latest, push to registry
▶ Show
Jenkins
pipeline {
    agent any
    environment {
        REGISTRY = 'registry.example.com'
        IMAGE    = "${REGISTRY}/myorg/myapp"
        CREDS    = credentials('docker-registry-creds')
    }
    stages {
        stage('Build Image') {
            steps {
                sh """

                      --build-arg VERSION=${env.BUILD_NUMBER} \

                sh "docker push ${IMAGE}:latest"
            }
        }
    }
    post { always { sh "docker logout ${REGISTRY}" } }
}

Rollback Strategies Quick recovery from failed deployments
▶ Show
# Strategy 1: K8s rollback
kubectl rollout undo deployment/myapp -n production

# Strategy 2: Redeploy previous good image
Jenkins
stage('Rollback') {
    when { expression { params.ROLLBACK == true } }
    steps {
        script {
            def previousTag = sh(script: """
                kubectl get deployment myapp -n prod \
                  -o jsonpath='{.metadata.annotations.previous-tag}'
            """, returnStdout: true).trim()
            sh "kubectl set image deployment/myapp myapp=${IMAGE}:${previousTag} -n prod"
        }
    }
}

# Best practices for pipeline maintenance:
1. Store Jenkinsfile / .gitlab-ci.yml in repo root
2. Use shared libraries / includes for common patterns
3. Pin versions (images, tools, plugins)
4. Keep pipelines under 10 minutes (cache + parallel)
5. Use branch protection rules for CI config changes
6. Template repetitive jobs (extends / YAML anchors)
7. Document required variables and secrets
8. Test pipeline changes in feature branches first

Security Best Practices Harden your CI/CD pipelines against supply chain attacks
▶ Show
1. Pin image digests (not just tags):
   image: maven@sha256:abc123...  # Immutable

2. Scan dependencies:
   - npm audit / mvn dependency-check:check / pip-audit

3. Sign artifacts:
   - cosign sign --key cosign.key $IMAGE:$TAG

4. Least-privilege runners:
   - Don't run as root
   - Limit network access
   - Use short-lived credentials

5. Protected branches/environments:
   - Require approval for production deploys
   - Restrict who can merge to main

6. Audit trail:
   - Log who triggered deploys
   - Track which image/commit is in each env

7. SAST/DAST in pipeline:
GitLab
include:
  - template: Security/SAST.gitlab-ci.yml
  - template: Security/Dependency-Scanning.gitlab-ci.yml
  - template: Security/Container-Scanning.gitlab-ci.yml
