Containers — Dockerfile, Compose, networking, security, optimization | Beginner to Advanced

1. Basics

Docker basics get you running containers in minutes — pulling images and starting isolated applications.

CommandDescriptionExample
docker run Create and start a container from an image
▶ Show
docker run nginx
docker run -d --name web nginx    # detached, named
docker run -it ubuntu bash         # interactive terminal
docker run -d -p 8080:80 nginx    # map host:container port
docker pull Download an image from a registry
▶ Show
docker pull ubuntu:22.04
docker pull python:3.11-slim
docker pull myregistry.io/app:latest
docker images List downloaded images
▶ Show
docker images                       # list all
docker images -q                    # IDs only
docker images --filter dangling=true # untagged images
docker ps List running containers
▶ Show
docker ps                           # running only
docker ps -a                        # all (including stopped)
docker ps -q                        # IDs only
docker ps --format "{{.Names}}: {{.Status}}"
docker version Show Docker client/server version
▶ Show
docker version
docker info    # detailed system info
💡 Tip: Use docker run --rm to auto-remove the container when it exits — great for one-off commands.

2. Container Lifecycle

Managing container state — starting, stopping, and cleaning up containers is your daily workflow.

CommandDescriptionExample
docker start Start a stopped container
▶ Show
docker start my-container
docker start -ai my-container  # attach + interactive
docker stop Gracefully stop a running container (SIGTERM → SIGKILL)
▶ Show
docker stop my-container
docker stop -t 5 my-container  # 5s timeout before SIGKILL
docker stop $(docker ps -q)    # stop all running
docker restart Restart a container
▶ Show
docker restart my-container
docker restart -t 10 my-container  # custom timeout
docker rm Remove stopped container(s)
▶ Show
docker rm my-container
docker rm -f my-container         # force remove (even running)
docker rm $(docker ps -aq)        # remove all stopped
docker container prune            # remove all stopped
docker logs View container output/logs
▶ Show
docker logs my-container
docker logs -f my-container       # follow (like tail -f)
docker logs --tail 50 my-container # last 50 lines
docker logs --since 1h my-container # last hour
docker kill Send signal to container (default: SIGKILL)
▶ Show
docker kill my-container
docker kill -s SIGUSR1 my-container
docker pause/unpause Freeze/unfreeze container processes
▶ Show
docker pause my-container
docker unpause my-container
docker rename Rename a container
▶ Show
docker rename old-name new-name
⚠️ Note: docker stop sends SIGTERM first, then SIGKILL after timeout (default 10s). Use docker kill for immediate termination.

3. Images

Images are the blueprints for containers. Building, tagging, and pushing them is how you package applications.

CommandDescriptionExample
docker build Build an image from a Dockerfile
▶ Show
docker build -t myapp:1.0 .         # tag and build from current dir
docker build -f Dockerfile.prod .   # specify Dockerfile
docker build --no-cache -t app .  # no layer cache
docker build --build-arg VERSION=2.0 -t app .
docker tag Create a new tag for an image
▶ Show
docker tag myapp:1.0 myapp:latest
docker tag myapp:1.0 registry.io/myapp:1.0
docker push Push an image to a registry
▶ Show
docker push registry.io/myapp:1.0
docker push myuser/myapp:latest
docker rmi Remove image(s)
▶ Show
docker rmi myapp:1.0
docker rmi $(docker images -q)         # remove all
docker image prune                     # remove dangling
docker image prune -a                 # remove all unused
docker history Show image layer history
▶ Show
docker history myapp:1.0
docker history --no-trunc myapp:1.0  # full commands
docker save/load Export/import images as tar archives
▶ Show
docker save -o myapp.tar myapp:1.0  # export
docker load -i myapp.tar             # import

4. Dockerfile Instructions

Dockerfile defines how your image is built — each instruction creates a layer that gets cached for fast rebuilds.

InstructionDescriptionExample
FROM Base image for the build stage
▶ Show
FROM ubuntu:22.04
FROM python:3.11-slim AS builder
FROM scratch  # empty base (for static binaries)
RUN Execute command during build (creates new layer)
▶ Show
RUN apt-get update && apt-get install -y curl
RUN pip install --no-cache-dir -r requirements.txt
# Multi-line for readability:
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
       curl wget \
    && rm -rf /var/lib/apt/lists/*
COPY Copy files from host to image
▶ Show
COPY . /app
COPY package.json package-lock.json ./
COPY --chown=node:node src/ /app/src/
COPY --from=builder /app/dist ./dist  # from another stage
ADD Like COPY but also handles URLs and auto-extracts archives
▶ Show
ADD app.tar.gz /opt/app/   # auto-extracts
ADD https://example.com/file.txt /tmp/
# Prefer COPY unless you need auto-extraction
WORKDIR Set working directory for subsequent instructions
▶ Show
WORKDIR /app
WORKDIR /app/src  # can be relative to previous WORKDIR
ENV Set environment variable (persists in running container)
▶ Show
ENV NODE_ENV=production
ENV PATH="/app/bin:$PATH"
ENV APP_PORT=8080 APP_HOST=0.0.0.0
ARG Build-time variable (not in running container)
▶ Show
ARG VERSION=1.0
ARG BASE_IMAGE=python:3.11
FROM ${BASE_IMAGE}
# Pass at build: docker build --build-arg VERSION=2.0 .
EXPOSE Document which port the container listens on
▶ Show
EXPOSE 8080
EXPOSE 8080/tcp 9090/udp
# Does NOT publish the port — use -p at runtime
CMD Default command when container starts (overridable)
▶ Show
# Exec form (preferred):
CMD ["python", "app.py"]
# Shell form:
CMD python app.py
# Can be overridden: docker run myapp python other.py
ENTRYPOINT Fixed executable; CMD becomes its arguments
▶ Show
ENTRYPOINT ["python"]
CMD ["app.py"]
# Result: python app.py
# Override args: docker run myapp other.py → python other.py
# Override entrypoint: docker run --entrypoint bash myapp
USER Set user for subsequent instructions and runtime
▶ Show
RUN useradd -r appuser
USER appuser
# or by UID/GID:
USER 1001:1001
HEALTHCHECK Define a health check command
▶ Show
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
HEALTHCHECK NONE  # disable inherited healthcheck
💡 Tip: Combine RUN commands with && to reduce layers. Always clean up package manager caches in the same RUN instruction.

5. Volumes & Storage

Volumes persist data beyond container lifecycle — essential for databases, uploads, and configuration.

Concept/CommandDescriptionExample
Named Volumes Docker-managed storage, persists after container removal
▶ Show
docker volume create mydata
docker run -v mydata:/app/data nginx
docker volume ls
docker volume inspect mydata
docker volume rm mydata
docker volume prune  # remove unused volumes
Bind Mounts Map host directory to container path
▶ Show
# Short syntax:
docker run -v $(pwd)/src:/app/src myapp

# --mount syntax (more explicit):
docker run --mount type=bind,source=$(pwd)/src,target=/app/src myapp

# Read-only bind mount:
docker run -v $(pwd)/config:/etc/config:ro myapp
tmpfs In-memory storage (not persisted, Linux only)
▶ Show
docker run --tmpfs /tmp myapp
docker run --mount type=tmpfs,target=/tmp,tmpfs-size=100m myapp
docker cp Copy files between container and host
▶ Show
docker cp mycontainer:/app/log.txt ./log.txt  # container → host
docker cp ./config.yml mycontainer:/etc/app/   # host → container
⚠️ Volumes vs Bind Mounts: Use named volumes for data persistence (databases, uploads). Use bind mounts for development (live code reload).

6. Networking

Docker networking controls how containers communicate with each other and the outside world.

Concept/CommandDescriptionExample
bridge (default) Isolated network; containers communicate via IP or linked names
▶ Show
# Default behavior — containers on same bridge can talk via IP
docker run -d --name web nginx
docker run -d --name api --link web myapi
host Container shares host's network stack (no isolation)
▶ Show
docker run --network host nginx
# No port mapping needed — uses host ports directly
# Linux only (macOS/Windows uses VM)
none No networking (fully isolated)
▶ Show
docker run --network none alpine ping google.com
# Will fail — no network access
Custom networks User-defined networks with DNS-based service discovery
▶ Show
docker network create mynet
docker run -d --name db --network mynet postgres
docker run -d --name app --network mynet myapp
# app can reach db via hostname "db"

docker network ls
docker network inspect mynet
docker network rm mynet
docker network connect mynet existing-container
Port mapping Expose container ports on host
▶ Show
docker run -p 8080:80 nginx          # host:container
docker run -p 127.0.0.1:8080:80 nginx # bind to localhost only
docker run -p 8080:80/udp nginx       # UDP port
docker run -P nginx                    # map all EXPOSE ports randomly
💡 Tip: Always use custom networks instead of --link (deprecated). Custom networks provide automatic DNS resolution between containers.

7. Docker Compose

Compose defines multi-container applications — your entire stack (app + db + cache) in one file.

Command/ConceptDescriptionExample
docker compose up Create and start all services
▶ Show
docker compose up                 # foreground
docker compose up -d              # detached
docker compose up --build         # rebuild images
docker compose up -d web api      # specific services
docker compose down Stop and remove containers, networks
▶ Show
docker compose down
docker compose down -v           # also remove volumes
docker compose down --rmi all    # also remove images
docker compose logs View logs from services
▶ Show
docker compose logs -f           # follow all
docker compose logs -f web       # follow specific service
compose.yml Full service definition example
▶ Show
# compose.yml
services:
  web:
    build: .
    ports:
      - "8080:80"
    environment:
      - NODE_ENV=production
    depends_on:
      - db
    volumes:
      - ./src:/app/src
    networks:
      - frontend
      - backend
    restart: unless-stopped

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: myapp
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

volumes:
  pgdata:

networks:
  frontend:
  backend:
depends_on Control startup order (with health conditions)
▶ Show
services:
  app:
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

  db:
    image: postgres:15
    healthcheck:
      test: ["CMD-SHELL", "pg_isready"]
      interval: 5s
      timeout: 3s
      retries: 5
docker compose ps/exec List services or exec into a service
▶ Show
docker compose ps
docker compose exec web bash
docker compose exec db psql -U postgres

8. Multi-stage Builds

Multi-stage builds create tiny production images by separating build tools from runtime — reducing attack surface and size.

Multi-stage builds let you use multiple FROM instructions to create intermediate images and copy only what you need into the final image — drastically reducing size.

PatternDescriptionExample
Basic multi-stage Build in one stage, run in another
▶ Show
# Stage 1: Build
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:18-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
Go static binary Build Go app, deploy on scratch (minimal image)
▶ Show
FROM golang:1.21 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app

FROM scratch
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
Java Maven Build with Maven, run with JRE only
▶ Show
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/*.jar /app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]
Target specific stage Build only up to a specific stage
▶ Show
docker build --target builder -t myapp:dev .
# Useful for CI/CD or dev images

9. Environment & Config

Environment variables externalize configuration — making the same image work across dev, staging, and production.

ConceptDescriptionExample
-e / --env Pass environment variables at runtime
▶ Show
docker run -e DB_HOST=localhost -e DB_PORT=5432 myapp
docker run -e API_KEY myapp  # passes from host env
--env-file Load env vars from a file
▶ Show
# .env file:
DB_HOST=postgres
DB_PORT=5432
DB_NAME=myapp

docker run --env-file .env myapp
Compose .env Environment variables in Docker Compose
▶ Show
# compose.yml
services:
  app:
    image: myapp
    environment:
      - DB_HOST=db
      - DB_PORT=5432
    env_file:
      - .env
      - .env.local

# Variable substitution in compose.yml:
services:
  app:
    image: myapp:${APP_VERSION:-latest}
    ports:
      - "${HOST_PORT:-8080}:80"
Docker Secrets Securely pass sensitive data (Swarm / Compose)
▶ Show
# compose.yml with secrets:
services:
  app:
    image: myapp
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt

# Secret is mounted at /run/secrets/db_password
Config files Mount configuration files into containers
▶ Show
docker run -v ./nginx.conf:/etc/nginx/nginx.conf:ro nginx
docker run -v ./app.yml:/app/config.yml:ro myapp
⚠️ Security: Never put secrets in ENV instructions in Dockerfiles — they persist in image layers. Use secrets, mount files at runtime, or use build secrets (--secret).

10. Registry & Push

Registries store and distribute images. Push to share with your team or deploy to production.

Command/ConceptDescriptionExample
docker login Authenticate to a registry
▶ Show
docker login                              # Docker Hub
docker login ghcr.io                      # GitHub Container Registry
docker login 123456.dkr.ecr.us-east-1.amazonaws.com  # AWS ECR
docker login -u user -p token registry.io
docker logout
Tag & Push Tag image for registry and push
▶ Show
# Docker Hub:
docker tag myapp:1.0 username/myapp:1.0
docker push username/myapp:1.0

# GitHub Container Registry:
docker tag myapp:1.0 ghcr.io/username/myapp:1.0
docker push ghcr.io/username/myapp:1.0

# AWS ECR:
docker tag myapp:1.0 123456.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
docker push 123456.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
Private Registry Run your own registry
▶ Show
# Run local registry:
docker run -d -p 5000:5000 --name registry registry:2

# Push to local registry:
docker tag myapp:1.0 localhost:5000/myapp:1.0
docker push localhost:5000/myapp:1.0

# Pull from local registry:
docker pull localhost:5000/myapp:1.0
AWS ECR Login Authenticate Docker to AWS ECR
▶ Show
# AWS CLI v2:
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456.dkr.ecr.us-east-1.amazonaws.com

11. Debugging

Debugging containers requires different techniques than traditional apps — exec, logs, and inspect are your tools.

CommandDescriptionExample
docker exec Run command inside a running container
▶ Show
docker exec -it mycontainer bash      # interactive shell
docker exec -it mycontainer sh        # if no bash available
docker exec mycontainer cat /etc/hosts
docker exec -u root mycontainer apt update  # as root
docker exec -w /app mycontainer ls    # set working dir
docker logs View stdout/stderr output
▶ Show
docker logs mycontainer
docker logs -f --tail 100 mycontainer    # follow last 100
docker logs --since "2024-01-01" mycontainer
docker logs --until "10m" mycontainer      # last 10 minutes
docker logs mycontainer 2>&1 | grep ERROR
docker inspect Detailed JSON metadata about container/image/network
▶ Show
docker inspect mycontainer
docker inspect --format '{{.State.Status}}' mycontainer
docker inspect --format '{{.NetworkSettings.IPAddress}}' mycontainer
docker inspect --format '{{json .Config.Env}}' mycontainer | jq
docker stats Live resource usage (CPU, memory, I/O)
▶ Show
docker stats                    # all containers
docker stats mycontainer         # specific container
docker stats --no-stream         # one-shot snapshot
docker stats --format "{{.Name}}: {{.CPUPerc}} {{.MemUsage}}"
docker top Show running processes inside container
▶ Show
docker top mycontainer
docker top mycontainer aux  # ps options
docker diff Show filesystem changes in container
▶ Show
docker diff mycontainer
# A = added, C = changed, D = deleted
docker events Real-time Docker daemon events
▶ Show
docker events
docker events --filter container=mycontainer
docker events --filter type=image
💡 Tip: For containers without a shell, use docker cp to extract files, or docker export container | tar -tf - to list the filesystem.

12. Security

Container security reduces attack surface — running as non-root, limiting capabilities, and scanning for vulnerabilities.

Concept/CommandDescriptionExample
Non-root user Run container as non-root for security
▶ Show
# In Dockerfile:
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# At runtime:
docker run --user 1001:1001 myapp
docker run --user nobody myapp
Read-only filesystem Prevent writes to container filesystem
▶ Show
docker run --read-only myapp
# Allow specific writable dirs:
docker run --read-only --tmpfs /tmp --tmpfs /var/run myapp
Capabilities Fine-grained Linux capability control
▶ Show
# Drop all capabilities, add only needed:
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp

# Common capabilities to drop:
docker run --cap-drop SYS_ADMIN --cap-drop NET_RAW myapp
Security options AppArmor, Seccomp, no-new-privileges
▶ Show
docker run --security-opt no-new-privileges myapp
docker run --security-opt seccomp=profile.json myapp
docker run --security-opt apparmor=docker-default myapp
Image scanning Scan images for vulnerabilities
▶ Show
docker scout quickview myapp:latest
docker scout cves myapp:latest
docker scout recommendations myapp:latest

# Third-party scanners:
trivy image myapp:latest
grype myapp:latest
Resource limits Prevent resource abuse
▶ Show
docker run --memory 512m --cpus 1.5 myapp
docker run --memory 1g --memory-swap 1g myapp  # no swap
docker run --pids-limit 100 myapp  # limit processes
Build secrets Pass secrets at build time without embedding in layers
▶ Show
# Dockerfile:
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci

# Build command:
docker build --secret id=npmrc,src=.npmrc -t myapp .

13. Optimization

Optimized images build faster, pull faster, and use less storage — critical for CI/CD pipelines and production.

TechniqueDescriptionExample
Layer caching Order instructions from least to most frequently changed
▶ Show
# ❌ Bad: COPY everything first (cache busts on any change)
COPY . /app
RUN npm install

# ✅ Good: Copy deps file first, install, then copy source
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
# Source changes don't invalidate npm install layer
.dockerignore Exclude files from build context (faster builds, smaller images)
▶ Show
# .dockerignore
node_modules
.git
.env
*.log
dist
.DS_Store
__pycache__
.pytest_cache
target/
*.class
Slim base images Use minimal base images to reduce size
▶ Show
# Image size comparison:
# node:18          ~900MB
# node:18-slim     ~200MB
# node:18-alpine   ~110MB

FROM python:3.11-slim     # instead of python:3.11
FROM eclipse-temurin:17-jre-alpine  # JRE only, Alpine
FROM gcr.io/distroless/java17  # Google's distroless
Minimize layers Combine RUN commands and clean up in same layer
▶ Show
# ❌ Bad: Multiple layers with leftover cache
RUN apt-get update
RUN apt-get install -y curl wget
RUN rm -rf /var/lib/apt/lists/*

# ✅ Good: Single layer, cleanup in same command
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl wget \
    && rm -rf /var/lib/apt/lists/*
Multi-stage for size Only copy production artifacts to final image
▶ Show
# Build stage has all dev tools (~1GB)
FROM node:18 AS builder
RUN npm ci && npm run build

# Final stage has only runtime (~100MB)
FROM node:18-alpine
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
Analyze image size Tools to inspect and reduce image size
▶ Show
# See layer sizes:
docker history myapp:latest

# Use dive (interactive layer explorer):
dive myapp:latest

# Check total size:
docker images myapp
💡 Tip: Always add a .dockerignore file. Without it, the entire build context (including node_modules, .git) gets sent to the Docker daemon.

14. Advanced

Advanced Docker features handle multi-architecture builds, health monitoring, and orchestration at scale.

Concept/CommandDescriptionExample
docker buildx Extended build capabilities (BuildKit)
▶ Show
# Create a builder instance:
docker buildx create --name mybuilder --use
docker buildx inspect --bootstrap

# Build with buildx:
docker buildx build -t myapp:latest --load .
docker buildx build -t myapp:latest --push .

# Build with cache export/import:
docker buildx build \
  --cache-from type=registry,ref=myapp:cache \
  --cache-to type=registry,ref=myapp:cache \
  -t myapp:latest --push .
Multi-arch builds Build for multiple CPU architectures (amd64, arm64)
▶ Show
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myuser/myapp:latest \
  --push .

# Check supported platforms:
docker buildx ls

# Inspect image manifest:
docker manifest inspect myuser/myapp:latest
HEALTHCHECK Container health monitoring
▶ Show
# In Dockerfile:
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

# At runtime:
docker run --health-cmd "curl -f http://localhost:8080/health" \
  --health-interval 30s --health-retries 3 myapp

# Check health status:
docker inspect --format '{{.State.Health.Status}}' mycontainer
docker ps --filter health=unhealthy
docker init Generate Dockerfile and compose.yml for your project
▶ Show
docker init
# Interactive wizard that detects project type
# Generates: Dockerfile, compose.yml, .dockerignore
# Supports: Node, Python, Go, Rust, Java, and more
Docker Swarm basics Native Docker clustering/orchestration
▶ Show
# Initialize swarm:
docker swarm init

# Deploy a service:
docker service create --name web --replicas 3 -p 80:80 nginx

# Scale service:
docker service scale web=5

# Deploy stack from compose file:
docker stack deploy -c compose.yml mystack

# List services:
docker service ls
docker service ps web

# Leave swarm:
docker swarm leave --force
System cleanup Reclaim disk space
▶ Show
# Remove all stopped containers, unused networks, dangling images, build cache:
docker system prune

# Nuclear option — remove everything unused:
docker system prune -a --volumes

# Check disk usage:
docker system df
docker system df -v  # verbose
Restart policies Auto-restart containers on failure or reboot
▶ Show
docker run --restart no myapp           # default (never)
docker run --restart always myapp       # always restart
docker run --restart unless-stopped myapp # unless manually stopped
docker run --restart on-failure:5 myapp  # max 5 retries
Docker contexts Manage multiple Docker hosts/endpoints
▶ Show
docker context ls
docker context create remote --docker "host=ssh://user@remote"
docker context use remote
docker ps  # now runs against remote host
⚠️ Note: Docker Swarm is simpler than Kubernetes for small deployments. For production at scale, consider Kubernetes, ECS, or Cloud Run.
