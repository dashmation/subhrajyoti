1. Cluster & Context

Contexts let you switch between multiple clusters (dev, staging, prod) safely without misconfiguring commands.

Command / ConceptDescriptionExample
kubectl config view Show merged kubeconfig settings
▶ Show
# View full kubeconfig (redacted secrets)
kubectl config view

# View raw (include tokens/certs)
kubectl config view --raw
kubectl config get-contexts List all available contexts
▶ Show
# List contexts (current marked with *)
kubectl config get-contexts

# Show only current context name
kubectl config current-context
kubectl config use-context Switch to a different context
▶ Show
# Switch to production cluster
kubectl config use-context prod-cluster

# Switch namespace within current context
kubectl config set-context --current --namespace=dev
kubectl config set-context Create or modify a context
▶ Show
# Create new context pointing to a cluster + user + namespace
kubectl config set-context my-ctx \
  --cluster=my-cluster \
  --user=my-user \
  --namespace=my-ns
kubectl config set-cluster Add or modify a cluster entry
▶ Show
# Add a new cluster
kubectl config set-cluster dev-cluster \
  --server=https://10.0.0.1:6443 \
  --certificate-authority=/path/to/ca.crt
kubectl cluster-info Display cluster endpoint info
▶ Show
# Basic cluster info
kubectl cluster-info

# Dump full cluster state for debugging
kubectl cluster-info dump
kubectl api-resources List all resource types available
▶ Show
# List all resources with their short names
kubectl api-resources

# Filter namespaced resources only
kubectl api-resources --namespaced=true

2. Pods

Pods are the smallest deployable unit — understanding them is essential before working with higher-level abstractions.

Command / ConceptDescriptionExample
kubectl run Create a pod imperatively
▶ Show
# Run an nginx pod
kubectl run nginx --image=nginx:1.25

# Run with labels and port
kubectl run web --image=nginx --port=80 --labels="app=web,env=dev"

# Dry-run to generate YAML
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml
kubectl get pods List pods in current namespace
▶ Show
# List pods with extra info
kubectl get pods -o wide

# All namespaces
kubectl get pods -A

# Watch for changes
kubectl get pods -w

# Filter by label
kubectl get pods -l app=nginx

# Custom columns output
kubectl get pods -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,IP:.status.podIP
kubectl describe pod Show detailed pod info & events
▶ Show
# Describe a specific pod
kubectl describe pod nginx

# Useful for debugging: check Events section at bottom
kubectl delete pod Remove a pod
▶ Show
# Delete single pod
kubectl delete pod nginx

# Force delete (skip graceful shutdown)
kubectl delete pod nginx --grace-period=0 --force

# Delete all pods with a label
kubectl delete pods -l app=test
kubectl logs View container logs
▶ Show
# Tail logs
kubectl logs nginx --tail=50

# Follow/stream logs
kubectl logs -f nginx

# Logs from specific container in multi-container pod
kubectl logs my-pod -c sidecar

# Previous container (after crash)
kubectl logs nginx --previous
kubectl exec Execute a command in a container
▶ Show
# Interactive shell
kubectl exec -it nginx -- /bin/bash

# Run a single command
kubectl exec nginx -- cat /etc/nginx/nginx.conf

# Specific container
kubectl exec -it my-pod -c sidecar -- sh
Pod YAML Declarative pod spec
▶ Show
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
spec:
  containers:
  - name: app
    image: my-app:1.0
    ports:
    - containerPort: 8080
    env:
    - name: ENV
      value: "production"
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"

3. Deployments

Deployments manage application lifecycle — rolling updates, scaling, and rollbacks with zero downtime.

Command / ConceptDescriptionExample
kubectl create deployment Create a deployment imperatively
▶ Show
# Create with 3 replicas
kubectl create deployment nginx --image=nginx:1.25 --replicas=3

# Generate YAML for editing
kubectl create deployment web --image=nginx --dry-run=client -o yaml > deploy.yaml
kubectl scale Scale replicas up or down
▶ Show
# Scale to 5 replicas
kubectl scale deployment nginx --replicas=5

# Scale multiple deployments
kubectl scale deployment/web deployment/api --replicas=3
kubectl rollout Manage deployment rollouts
▶ Show
# Check rollout status
kubectl rollout status deployment/nginx

# View rollout history
kubectl rollout history deployment/nginx

# Pause / Resume rollout
kubectl rollout pause deployment/nginx
kubectl rollout resume deployment/nginx
kubectl set image Update container image (triggers rollout)
▶ Show
# Update image
kubectl set image deployment/nginx nginx=nginx:1.26

# Record the change (for history)
kubectl set image deployment/nginx nginx=nginx:1.26 --record
kubectl rollout undo Rollback to previous revision
▶ Show
# Rollback to previous
kubectl rollout undo deployment/nginx

# Rollback to specific revision
kubectl rollout undo deployment/nginx --to-revision=2
Deployment YAML Declarative deployment with strategy
▶ Show
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # max extra pods during update
      maxUnavailable: 0    # zero downtime
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web
        image: my-app:2.0
        ports:
        - containerPort: 8080

4. Services

Services provide stable networking to pods — since pods are ephemeral, services give them a permanent address.

Services provide stable networking for pods. DNS: service-name.namespace.svc.cluster.local
Command / ConceptDescriptionExample
ClusterIP Internal-only access (default type)
▶ Show
# Expose deployment as ClusterIP
kubectl expose deployment nginx --port=80 --target-port=8080

# YAML
apiVersion: v1
kind: Service
metadata:
  name: my-svc
spec:
  type: ClusterIP
  selector:
    app: web-app
  ports:
  - port: 80
    targetPort: 8080
NodePort Expose on each node's IP at a static port (30000-32767)
▶ Show
# Expose as NodePort
kubectl expose deployment nginx --type=NodePort --port=80

# YAML
apiVersion: v1
kind: Service
metadata:
  name: my-nodeport
spec:
  type: NodePort
  selector:
    app: web-app
  ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080    # optional, auto-assigned if omitted
LoadBalancer Provision external LB (cloud providers)
▶ Show
# Expose with cloud load balancer
kubectl expose deployment nginx --type=LoadBalancer --port=80

# YAML with annotations (AWS NLB example)
apiVersion: v1
kind: Service
metadata:
  name: my-lb
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
spec:
  type: LoadBalancer
  selector:
    app: web-app
  ports:
  - port: 443
    targetPort: 8443
ExternalName Map service to external DNS name (CNAME)
▶ Show
# Point to external database
apiVersion: v1
kind: Service
metadata:
  name: ext-db
spec:
  type: ExternalName
  externalName: db.example.com
kubectl get svc List services
▶ Show
kubectl get svc -o wide
kubectl get endpoints my-svc  # see pod IPs behind service

5. ConfigMaps & Secrets

Externalize configuration from images — change behavior without rebuilding, and protect sensitive data.

Command / ConceptDescriptionExample
kubectl create configmap Create ConfigMap from literals or files
▶ Show
# From literal values
kubectl create configmap app-config \
  --from-literal=DB_HOST=postgres \
  --from-literal=DB_PORT=5432

# From a file
kubectl create configmap nginx-conf --from-file=nginx.conf

# From env file
kubectl create configmap env-config --from-env-file=.env
ConfigMap YAML Declarative ConfigMap
▶ Show
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "postgres"
  DB_PORT: "5432"
  app.properties: |
    server.port=8080
    logging.level=INFO
Use ConfigMap in Pod Inject as env vars or volume
▶ Show
# As environment variables
spec:
  containers:
  - name: app
    image: my-app
    envFrom:
    - configMapRef:
        name: app-config

# As mounted volume
spec:
  containers:
  - name: app
    image: my-app
    volumeMounts:
    - name: config-vol
      mountPath: /etc/config
  volumes:
  - name: config-vol
    configMap:
      name: app-config
kubectl create secret Create a Secret (base64-encoded)
▶ Show
# Generic secret from literals
kubectl create secret generic db-creds \
  --from-literal=username=admin \
  --from-literal=password=s3cr3t

# TLS secret
kubectl create secret tls my-tls \
  --cert=tls.crt --key=tls.key

# Docker registry secret
kubectl create secret docker-registry regcred \
  --docker-server=registry.io \
  --docker-username=user \
  --docker-password=pass
Secret YAML Declarative Secret (values base64)
▶ Show
apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
data:
  username: YWRtaW4=        # echo -n 'admin' | base64
  password: czNjcjN0        # echo -n 's3cr3t' | base64
---
# Use stringData for plain text (auto-encoded)
apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
stringData:
  username: admin
  password: s3cr3t
Use Secret in Pod Inject as env or volume mount
▶ Show
# Single key as env var
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-creds
      key: password

# All keys as env vars
envFrom:
- secretRef:
    name: db-creds

# As volume (files)
volumes:
- name: secret-vol
  secret:
    secretName: db-creds

6. Volumes

Volumes provide persistent storage that survives pod restarts — required for databases and stateful applications.

Command / ConceptDescriptionExample
emptyDir Ephemeral volume, shared between containers in a pod
▶ Show
spec:
  containers:
  - name: app
    image: my-app
    volumeMounts:
    - name: cache
      mountPath: /tmp/cache
  - name: sidecar
    image: log-agent
    volumeMounts:
    - name: cache
      mountPath: /data
  volumes:
  - name: cache
    emptyDir: {}          # deleted when pod is removed
hostPath Mount a directory from the host node
▶ Show
volumes:
- name: host-data
  hostPath:
    path: /var/log/app
    type: DirectoryOrCreate   # creates if missing
PersistentVolume (PV) Cluster-wide storage resource
▶ Show
apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce        # RWO, ROX, RWX
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  hostPath:
    path: /mnt/data
PersistentVolumeClaim (PVC) Request storage from a PV
▶ Show
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
---
# Use in Pod
spec:
  containers:
  - name: app
    volumeMounts:
    - name: data
      mountPath: /var/data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc
StorageClass Dynamic provisioning of PVs
▶ Show
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iopsPerGB: "50"
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

# PVC referencing StorageClass
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: fast-storage
spec:
  storageClassName: fast-ssd
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 20Gi
kubectl get pv,pvc List volumes and claims
▶ Show
kubectl get pv
kubectl get pvc
kubectl describe pvc my-pvc   # check binding status

7. Namespaces & RBAC

Namespaces isolate workloads (teams/environments). RBAC controls who can do what in the cluster.

Command / ConceptDescriptionExample
kubectl create namespace Create a namespace for isolation
▶ Show
kubectl create namespace dev
kubectl create namespace staging
kubectl create namespace prod

# List namespaces
kubectl get namespaces

# Delete namespace (deletes all resources in it!)
kubectl delete namespace dev
ResourceQuota Limit resources per namespace
▶ Show
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    pods: "20"
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: "5"
Role Namespace-scoped permissions
▶ Show
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
RoleBinding Bind Role to a user/group/SA
▶ Show
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: jane
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
ClusterRole / ClusterRoleBinding Cluster-wide permissions
▶ Show
# ClusterRole for node access
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-viewer
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: view-nodes
subjects:
- kind: Group
  name: ops-team
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: node-viewer
  apiGroup: rbac.authorization.k8s.io
ServiceAccount Identity for pods to interact with API
▶ Show
# Create service account
kubectl create serviceaccount my-app-sa -n dev

# Use in pod spec
spec:
  serviceAccountName: my-app-sa
  containers:
  - name: app
    image: my-app

# Check permissions
kubectl auth can-i get pods --as=system:serviceaccount:dev:my-app-sa

8. DaemonSets, StatefulSets, Jobs, CronJobs

Specialized workloads handle specific patterns — one-per-node, ordered deployment, and batch processing.

Command / ConceptDescriptionExample
DaemonSet Run one pod per node (logs, monitoring agents)
▶ Show
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      name: fluentd
  template:
    metadata:
      labels:
        name: fluentd
    spec:
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluentd:v1.16
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
StatefulSet Ordered, stable pods with persistent storage
▶ Show
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: "postgres"     # headless service name
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:16
        ports:
        - containerPort: 5432
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:       # each pod gets its own PVC
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
---
# Headless service for StatefulSet
apiVersion: v1
kind: Service
metadata:
  name: postgres
spec:
  clusterIP: None             # headless
  selector:
    app: postgres
  ports:
  - port: 5432
Job Run to completion, then stop
▶ Show
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  backoffLimit: 3              # retries on failure
  activeDeadlineSeconds: 600   # timeout
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: my-app:migrate
        command: ["python", "migrate.py"]

# Parallel job (process 10 items, 3 at a time)
---
apiVersion: batch/v1
kind: Job
metadata:
  name: batch-process
spec:
  completions: 10
  parallelism: 3
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: worker:1.0
CronJob Scheduled jobs (cron syntax)
▶ Show
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"       # 2 AM daily
  concurrencyPolicy: Forbid   # skip if previous still running
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: backup-tool:latest
            command: ["/bin/sh", "-c", "pg_dump ... | gzip > /backup/db.gz"]
kubectl get List workloads
▶ Show
kubectl get daemonsets
kubectl get statefulsets
kubectl get jobs
kubectl get cronjobs

9. Ingress & Network Policies

Ingress exposes HTTP services externally. Network policies act as firewalls between pods.

Command / ConceptDescriptionExample
Ingress HTTP/HTTPS routing to services (requires controller)
▶ Show
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - app.example.com
    secretName: tls-secret
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-svc
            port:
              number: 80
Ingress (multiple hosts) Route different domains to different services
▶ Show
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 8080
  - host: admin.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-service
            port:
              number: 3000
NetworkPolicy (Ingress) Control inbound traffic to pods
▶ Show
# Allow traffic only from frontend to backend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
NetworkPolicy (Egress) Control outbound traffic from pods
▶ Show
# Allow egress only to specific CIDR and DNS
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-egress
spec:
  podSelector:
    matchLabels:
      app: secure-app
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        cidr: 10.0.0.0/8
    ports:
    - protocol: TCP
      port: 5432
  - to:                        # allow DNS
    - namespaceSelector: {}
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
Default Deny All Zero-trust baseline policy
▶ Show
# Deny all ingress and egress in a namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

10. Health Checks (Probes)

Probes tell Kubernetes when your app is ready for traffic and when it needs a restart — essential for reliability.

Liveness: restart if failing | Readiness: remove from Service endpoints | Startup: delay other probes until app is ready
Command / ConceptDescriptionExample
Liveness Probe (HTTP) Restart container if health endpoint fails
▶ Show
containers:
- name: app
  image: my-app:1.0
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    initialDelaySeconds: 15
    periodSeconds: 10
    failureThreshold: 3
    timeoutSeconds: 5
Readiness Probe (TCP) Only send traffic when port is open
▶ Show
containers:
- name: db
  image: postgres:16
  readinessProbe:
    tcpSocket:
      port: 5432
    initialDelaySeconds: 5
    periodSeconds: 10
Startup Probe For slow-starting apps (disables other probes until success)
▶ Show
containers:
- name: legacy-app
  image: legacy:3.0
  startupProbe:
    httpGet:
      path: /ready
      port: 8080
    failureThreshold: 30     # 30 * 10s = 5 min max startup
    periodSeconds: 10
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    periodSeconds: 10
Exec Probe Run a command inside the container
▶ Show
containers:
- name: app
  image: my-app
  livenessProbe:
    exec:
      command:
      - cat
      - /tmp/healthy
    initialDelaySeconds: 5
    periodSeconds: 5
gRPC Probe Native gRPC health check (K8s 1.24+)
▶ Show
containers:
- name: grpc-server
  image: my-grpc:1.0
  livenessProbe:
    grpc:
      port: 50051
      service: ""            # empty = overall health
    initialDelaySeconds: 10
    periodSeconds: 10

11. Resource Management

Resource requests/limits prevent noisy neighbors and enable autoscaling based on actual demand.

Command / ConceptDescriptionExample
Requests & Limits CPU/memory guarantees and caps per container
▶ Show
containers:
- name: app
  image: my-app
  resources:
    requests:               # scheduler guarantee
      cpu: "250m"           # 0.25 CPU cores
      memory: "128Mi"
    limits:                 # hard cap (OOMKilled if exceeded)
      cpu: "500m"
      memory: "256Mi"

# CPU: 1000m = 1 core | Memory: Mi, Gi
LimitRange Default/min/max per container in namespace
▶ Show
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: dev
spec:
  limits:
  - type: Container
    default:              # applied if none specified
      cpu: "500m"
      memory: "256Mi"
    defaultRequest:
      cpu: "100m"
      memory: "64Mi"
    max:
      cpu: "2"
      memory: "1Gi"
    min:
      cpu: "50m"
      memory: "32Mi"
HorizontalPodAutoscaler (HPA) Auto-scale replicas based on metrics
▶ Show
# Imperative
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10

# Declarative (v2 API)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:

Common Debug Patterns Troubleshooting workflow
▶ Show
# 1. Pod stuck in Pending?
kubectl describe pod <name>   # check Events → scheduling
kubectl get nodes             # check node capacity

# 2. CrashLoopBackOff?
kubectl logs <pod> --previous # check exit reason
kubectl describe pod <name>   # check exit code

# 3. ImagePullBackOff?
kubectl describe pod <name>   # check image name/registry
kubectl get secrets           # verify imagePullSecrets

# 4. Service not reachable?
kubectl get endpoints <svc>   # check if pods are selected
kubectl run tmp --rm -it --image=busybox -- wget -qO- <svc>:<port>

# 5. DNS not resolving?
kubectl run tmp --rm -it --image=busybox -- nslookup kubernetes.default
